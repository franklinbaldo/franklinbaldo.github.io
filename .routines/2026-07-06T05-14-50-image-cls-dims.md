Escolhi **#553** (audit de dimensões explícitas em imagens para CLS), a mais antiga do
lote, por ter maior potencial de impacto real em Core Web Vitals.

Investigação (via agente Explore): o `<Image>` do Astro e o pipeline de assets do
Astro já dimensionam corretamente imagens **locais** em markdown — não existe nenhuma
imagem local hoje no repo, então essa parte do issue já estava coberta de graça.
O gap real é só **imagens remotas** (`![alt](https://...)`), que escapam do pipeline
de assets. Auditei `src/content/blog/**` inteiro e encontrei ~20 URLs únicas, todas em
`api.memegen.link` (memes-piada em ~13 arquivos de versão, incluindo posts publicados
como *Census, Not Sample* e *Pierre Menard, Computational Researcher*).

Implementação:
- `scripts/generate-image-dimensions.mjs` (novo): varre os posts, busca cada URL
  remota única, mede dimensão real via `image-size` (novo dep) e grava
  `src/generated/image-dimensions.json`. Deliberadamente **fora do `prebuild`** —
  acoplar todo build a uma dependência de rede (memegen.link) seria frágil demais
  para CI; roda-se manualmente quando um post novo referencia imagem remota, mesmo
  padrão de "rodar localmente" que `hronir:select` já usa em outro contexto.
- `astro.config.mjs`: o plugin `rehypeLazyImages` (que só injetava `loading="lazy"`)
  agora também lê o cache e injeta `width`/`height` reais quando disponíveis — nunca
  valores arbitrários, respeitando o invariante do issue. Cache ausente = mesmo
  comportamento de hoje (sem quebrar nada).

Achado incidental durante a geração do cache: 2 das ~20 URLs (`brain/...`) retornam
404 — o template `brain` do memegen.link foi renomeado para `gb` ("Galaxy Brain") após
a publicação dos posts `everything-is-eml` e `tree-reads-itself`, então essas duas
imagens já quebram silenciosamente em produção hoje (ícone de imagem quebrada). Isso é
uma correção de conteúdo, fora do escopo deste PR — abri a issue #979 (`routine`,
`priority:baixa`) para isso.
