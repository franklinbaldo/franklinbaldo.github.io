There is an unwritten rule in computer science: _if something processes information, someone will try to run Doom on it_. Here the experiment is slightly different: we use a **filtered, compact representation of the MaleCNS connectome** as a recurrent operator inside an embodied agent navigating a Doom-like arena.

Three quantities must be kept separate:

- **render FPS**: how often the arena is drawn;
- **neural steps/s**: how often the connectome state is actually updated in the embodied loop;
- **kernel throughput**: how many recurrent steps the isolated kernel can execute in a benchmark.

They are not equivalent. The current interactive demo schedules neural updates at roughly **25 Hz** (one step every ~40 ms), while rendering can run much faster. Any hundreds-of-steps-per-second figure belongs to an isolated kernel benchmark unless explicitly stated otherwise.

## 1. What is actually being simulated

The MaleCNS source dataset is larger than the representation used here. The experiment should not present **165,122 neurons / 10.2 million connections** as an unqualified statement of the raw dataset size.

Our pipeline derives a working representation and applies further filtering for the compact kernel. The compressed version retains roughly **1.54 million edges**. That matters because pruning also reduces the amount of computation per recurrent step.

Performance claims therefore need to separate:

1. speed gained by **executing fewer edges**;
2. speed gained by **representing the same edges differently**.

Without that decomposition, it is not valid to attribute the full throughput gain to cache residency.

---

## 2. Compact representation

The compact form combines:

1. edge filtering according to the pipeline threshold;
2. `uint16` delta encoding for source indices;
3. a quantized weight codebook, currently packed at 4 bits per edge;
4. FlatBuffers (`.mcns`) as the compact distribution format.

The resulting file is about **4.98 MB**.

Two caveats matter. First, a 4.98 MB graph does not imply the entire working set remains resident in an 8 MB L3 cache. Each fly also maintains `state`, `nextState`, and `drive` `Float32Array`s. Second, the current browser path copies typed-array slices before sending them to the Web Worker, so **"zero-copy" does not describe the JavaScript pipeline end-to-end**.

---

## 3. Benchmark one change at a time

The corrected benchmark is an ablation ladder using the same edge set whenever representation is the variable:

| Stage | Graph | Index representation | Weight representation | Question |
| --- | --- | --- | --- | --- |
| A | 1.54M edges | CSR 32-bit | FP32 | pruned-graph baseline |
| B | same | delta `uint16` | FP32 | value of index compression |
| C | same | delta `uint16` | LUT `uint8` | codebook without nibble unpacking |
| D | same | delta `uint16` | packed 4-bit LUT | is 4-bit actually faster? |
| E | full vs pruned | same | same | how much speed came from pruning? |

This distinguishes **less work**, **less memory traffic**, and **decompression overhead**.

The 8-bit-vs-4-bit comparison is especially useful. Packed 4-bit weights are smaller, but every edge requires a shift, mask, and lookup. A slightly larger 8-bit codebook can plausibly be faster. That is an empirical question.

---

## 4. Corrected sensory-motor experiment

The arena produces ray-cast visual signals and bilateral odor cues that are projected into mapped sensory populations. The recurrent state then drives descending-neuron readout.

The earlier demo also added several hand-written sensor-to-motor shortcuts directly to the connectome output:

- direct phototaxis (`visualSteer`);
- direct chemotaxis (`odorSteer`);
- explicit wall-avoidance `saccade`;
- `odorSurge` added directly to forward thrust.

Those paths are useful as an engineering controller baseline, but they must not be silently mixed into the connectome when asking whether biological topology contributes control.

The corrected experiment therefore treats these as explicit ablations:

| brain | hand-written sensor→motor controller | purpose |
| --- | --- | --- |
| MaleCNS | off | connectome-only control |
| degree-preserving shuffled | off | topology control |
| none | on | heuristic-controller baseline |
| MaleCNS | on | incremental contribution over the baseline |

Only comparisons with the same external policy can be attributed to topology.

---

## 5. Null-model requirements

The shuffled control must state exactly what it preserves. The repository already uses a directed double-edge-swap control in the MaleCNS tagger experiments that preserves per-node in-degree, per-node out-degree, edge count, and the edge-weight multiset while changing higher-order wiring.

For FlyDoom, paired runs should additionally use the same:

- sensory projection;
- motor decoder;
- random seed;
- spawn sequence;
- number of ticks;
- collision and reward definitions.

A single run should not be framed as proof that a biological connectome "plays Doom." The narrower, testable question is: **under a fixed interface and fixed seeds, does MaleCNS topology perform differently from pre-specified null models?**

---

## 6. Optimization hypotheses

The next optimization work is now phrased as measured hypotheses:

- packed 4-bit LUT vs unpacked 8-bit LUT;
- transferable buffers or `SharedArrayBuffer` to remove avoidable copies;
- WASM/SIMD for the recurrent hot loop;
- `tanh` approximation/LUT with numerical and behavioral error measured;
- neuron-major multi-fly layout for SIMD;
- graph reordering for locality without changing edges;
- multithreading only after synchronization cost is measured.

The goal is no longer one impressive FPS number. It is a reproducible chain of evidence for **what made the system faster, what approximation error was introduced, and what part of behavior came from the connectome rather than the external controller**.
